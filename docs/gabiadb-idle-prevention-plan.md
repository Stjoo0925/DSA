# 가비아 DB 유휴 상태 방지 자동화 시스템 구축 기획서

## 1. 프로젝트 개요

본 프로젝트는 가비아 PostgreSQL 데이터베이스가 장시간 요청이 없을 경우 유휴 상태에 진입하여, 이후 수동 조치가 있어야 정상 동작하는 문제를 해결하기 위한 자동화 시스템 구축을 목적으로 한다. 현재는 운영자가 [pgAdmin](http://pg1101.gabiadb.com/pgadmin/)에 접속하여 로그인한 뒤 `gnss_device` 테이블에 접근하고, 특정 조회 쿼리를 실행해야 DB가 다시 활성화되는 방식으로 대응하고 있다. 이러한 수동 운영 절차를 제거하고 서비스 안정성을 확보하기 위해, Go 기반 배치 프로그램을 서버에 배포하고 정해진 주기로 DB 활성화용 쿼리를 자동 실행하는 구조를 도입하고자 한다.

## 2. 추진 배경 및 필요성

현행 운영 방식은 DB가 장시간 무동작 상태일 때 실서비스에서 즉시 응답하지 못하는 문제가 발생할 수 있으며, 이를 해소하기 위해 운영자가 직접 관리자 페이지에 접속해 수동으로 쿼리를 수행해야 한다. 이 방식은 반복적인 운영 부담을 발생시키고, 비운영 시간대 대응 지연, 장애 감지 한계, 운영 리스크 증가로 이어진다. 따라서 유휴 상태 진입 자체를 예방하고, 장애 여부를 자동으로 감시하며, 운영 결과를 일일 단위로 보고할 수 있는 경량 자동화 체계가 필요하다.

## 3. 프로젝트 목적

- 가비아 PostgreSQL DB의 유휴 상태 진입 방지
- 수동 접속 및 쿼리 실행 절차 제거
- 장애 발생 여부의 자동 감지 및 통보
- 일일 운영 현황 자동 보고 체계 구축
- 실제 효과가 있는 최소 쿼리 검증을 통한 운영 정책 최적화

## 4. 현행 운영 방식

현재 DB 유휴 상태 해소 절차는 아래와 같다.

1. 운영자가 [pgAdmin](http://pg1101.gabiadb.com/pgadmin/)에 접속
2. 관리자 계정으로 로그인
3. `gnss_device` 테이블 진입
4. `Browse` 기능을 통해 아래 쿼리 실행

```sql
SELECT * FROM "public"."gnss_device";
```

5. 이후 DB가 다시 정상 동작

이 절차는 일회성 대응에는 유효하나, 운영 효율성과 안정성 측면에서 지속 가능한 방식이 아니다.

## 5. 구축 방향

자동화 시스템은 별도의 내부 운영 DB 없이 구성한다. 본 프로젝트는 데이터 저장이나 복잡한 상태 관리가 목적이 아니라, 외부 PostgreSQL에 주기적으로 접속하여 유휴 상태를 방지하고 결과를 기록하는 것이 핵심이므로, 별도 경량 DB조차 도입하지 않는 것이 가장 단순하고 실용적이다.

구성 방향은 다음과 같다.

- Go 기반 단일 배치 프로그램 개발
- 외부 PostgreSQL 접속 정보는 환경변수로 관리
- 3시간 주기 스케줄 실행
- 3종의 SQL을 순차 실행하며 성공/실패 이력 수집
- 실패 조건 충족 시 웹훅 기반 메신저 알림 발송
- 매일 오전 9시 전일 기준 일일 보고서 발송
- 로그는 최대 1주일 보관

## 6. 시스템 구성 방안

### 6.1 전체 구성

시스템은 다음 요소로 구성된다.

- Go 배치 프로그램
- 서버 스케줄러
- 가비아 PostgreSQL
- 로그 저장
- 메신저 웹훅 연동

배포 서버는 특정 제약 없이, 외부에서 가비아 DB에 접속 가능한 서버라면 어느 곳이든 사용 가능하다. 별도의 고사양 인프라는 필요하지 않으며, 상시 운영 가능한 일반 서버면 충분하다.

### 6.2 실행 구조

본 시스템은 2개의 자동화 흐름으로 운영된다.

1. 유휴 방지 실행 작업
   3시간마다 실행되어 DB 접속 후 3종의 쿼리를 순차 수행한다.
2. 일일 보고 작업
   매일 오전 9시에 전일 실행 결과를 집계하여 메신저 웹훅으로 보고서를 발송한다.

## 7. 실행 쿼리 정책

초기 운영 단계에서는 유휴 방지에 실제 효과가 있는 최소 수준의 쿼리를 검증하기 위해, 난이도와 부하 수준이 다른 3종의 SQL을 순차적으로 실행한다.

```sql
SELECT 1;
SELECT 1 FROM "public"."gnss_device" LIMIT 1;
SELECT * FROM "public"."gnss_device";
```

이 방식의 목적은 다음과 같다.

- 단순 연결 확인 수준의 쿼리로도 효과가 있는지 검증
- 실제 대상 테이블 접근이 필요한지 확인
- 현재 수동 대응과 동일한 전체 조회까지 필요한지 비교 검증
- 운영 데이터를 기반으로 향후 최종 고정 쿼리를 선정

초기에는 3종 모두 실행하되, 일정 기간 운영 후 성공 패턴과 효과를 분석하여 최종적으로 1개 쿼리만 사용하는 방식으로 단순화할 수 있다.

## 8. 운영 정책

### 8.1 실행 주기

유휴 방지 작업은 3시간마다 1회 실행한다.
일일 보고 작업은 매일 오전 9시에 1회 실행한다.

### 8.2 실패 기준

아래 항목은 모두 실패로 간주한다.

- DB 접속 실패
- 쿼리 실행 타임아웃
- SQL 에러 발생

### 8.3 타임아웃 정책

각 쿼리 실행에는 최대 5초의 타임아웃을 적용한다.
5초 내 정상 응답이 없을 경우 해당 쿼리는 실패 처리한다.

### 8.4 재시도 정책

개별 쿼리 실행이 실패할 경우 1회에 한해 재시도한다.
재시도 후에도 실패하면 최종 실패로 기록한다.

### 8.5 알림 정책

웹훅 기반 장애 알림은 개별 쿼리 실패 시마다 발송하지 않는다.
동일 실행 주기 내 3개 쿼리가 모두 실패한 경우에만 메신저 알림을 발송한다.

이 정책은 부분 실패에 따른 과도한 알림을 방지하고, 실제 장애 가능성이 높은 상황에만 운영자가 집중할 수 있도록 하기 위함이다.

### 8.6 로그 보관 정책

실행 로그는 최대 1주일간 보관한다.
보관 기간이 지난 로그는 자동 삭제하거나 순환 관리한다.

## 9. 로그 및 보고 체계

### 9.1 실행 로그 항목

각 실행 시 아래 정보를 기록한다.

- 실행 시각
- 실행 대상 쿼리
- 쿼리별 성공/실패 여부
- 응답 시간
- 재시도 여부
- 최종 에러 메시지
- 전체 실행 결과

### 9.2 일일 보고 기준

매일 오전 9시에 전일 기준 실행 결과를 집계하여 웹훅을 통해 메신저로 발송한다. 보고 항목은 다음과 같다.

- 총 실행 횟수
- 쿼리별 성공 횟수
- 쿼리별 실패 횟수
- 마지막 실패 시각
- 주요 에러 요약

일일 보고는 단순한 상태 공유를 넘어, 어떤 쿼리가 실제 유휴 방지에 효과적인지 판단하는 운영 근거 자료로 활용한다.

## 10. 장애 대응 방안

장애 대응은 웹훅 기반 메신저 알림으로 수행한다.
3개 쿼리가 모두 실패한 경우, 즉시 아래 수준의 정보를 포함해 메신저로 발송한다.

- 장애 발생 시각
- 접속 대상 DB 정보 또는 식별값
- 실행한 3개 쿼리의 결과 요약
- 최종 에러 메시지
- 재시도 수행 여부

이를 통해 운영자는 별도 시스템 접속 없이 메신저만으로도 장애 징후를 빠르게 확인할 수 있다.

- 장애 대응 자동화

- Slack, Teams, Discord 등 메신저별 포맷 최적화

## 15. 결론

본 프로젝트는 가비아 PostgreSQL의 유휴 상태 문제를 수동 대응에서 자동 운영 체계로 전환하는 데 목적이 있다. Go 기반의 경량 배치 프로그램을 활용하여 3시간마다 DB를 자동 점검 및 활성화하고, 실패 상황은 웹훅으로 즉시 통보하며, 일일 운영 결과는 오전 9시에 자동 보고하도록 설계한다. 또한 초기에는 3종 쿼리를 병행 운영하여 실제로 효과가 있는 최소 쿼리를 검증하고, 향후 운영 데이터를 바탕으로 최적 방식으로 고정할 수 있도록 한다. 이로써 서비스 안정성과 운영 효율을 동시에 확보할 수 있다.
